1. 目的

依頼内容は次の4点。

  1. ピース状態（editorUi.primaryTool === 'piece'）に、カレントミノ選択重視のUIと テトリス操作重視のUIの切り替え機能を追加する。
  2. 選択重視ではNEXT／HOLDキューを表示しない。右列はPAINT状態・SELECT状態に近いボタン群にする。
  3. 操作重視では、添付画像（他テトリスライククライアント）と同じ比率のNEXT／HOLDキューとフィールドにする。
  4. 切り替えはピース状態に表示されたトグルで行う。

背景は「NEXT／HOLDキューが狭い」という体感で、これは現状の実装から数値で裏付けられる。 現在のPIECE状態は1つの右列にNEXT枠・∞7bag・レール（モード2行＋パレット10行）を全部積む設計のため、 キューの幅も高さもレールに従属している。

つまり狭さの正体は主に次の2つで、どちらも「1列にパレットを同居させている」ことが原因である。

  • 幅：getPieceSideWidth() の上限が80pxで固定されている。PC・デスクトップでは盤面が高さ律速のため 左右に180px以上の余白が残っているのに、キューは80pxで頭打ちになる（1920幅で比率0.20）。
  • 高さ：右列の縦方向予算をパレット10行＋モード2行が食う（PCで32px×12行＝384px）。 残りをNEXT5個で割るため、PCではミノ1個26pxまで潰れる。

一方で「カレントミノを選んで置く」使い方（＝現在のパレット主体の操作）では、NEXT／HOLDはそもそも不要である。 そこで2つの用途を1画面に同居させるのをやめ、レイアウトを切り替えるのが本設計の方針である。 パレット10行とキューは、同じ縦方向予算を奪い合う関係にあるため、排他にすると双方が広くなる。

3-5. 新しいレイアウト計算

(a) 操作重視：列幅を「盤面のマス」基準にする

添付画像のキュー枠はいずれも盤面3.3〜3.7マス幅である（ミノ最大4マス＋余白）。 そこで固定px上限ではなく、盤面1マス unit = blockSize + 1 の倍数で決める。 盤面幅 10.5 unit 相当と左右2列 2 × 3.4 unit を同時に解くと、幅律速時のマス寸法が一意に決まる。 

// responsive_layout.ts（新規・抜粋）
export const PIECE_QUEUE_COLUMN_UNITS = 3.4;   // キュー列幅＝盤面3.4マス
export const MIN_PIECE_QUEUE_WIDTH = 66;
export const MAX_PIECE_QUEUE_WIDTH = 132;
export const PIECE_LAYOUT_TOGGLE_HEIGHT = 26;
export const PLAY_RAIL_ROWS = 3;               // [PIECE|AI] [SELECT|PAINT] [DEL|RESPAWN|RESET]
export const PLAY_RAIL_CHROME_HEIGHT = 20;     // 3グループの枠線＋グループ間gap
export const MAX_PLAY_NEXT_MINO_HEIGHT = 96;
export const MIN_PLAY_NEXT_MINO_HEIGHT = 20;

// 幅律速時のマス寸法：canvasWidth = 10.5u + 2 × 3.4u + gaps
export const getPlayPieceUnitBound = (canvasWidth: number, gap: number): number => (
    (canvasWidth - gap - PIECE_RIGHT_COLUMN_GAP) / (10.5 + 2 * PIECE_QUEUE_COLUMN_UNITS)
);

export const getPlayPieceQueueWidth = (unit: number): number => Math.min(
    MAX_PIECE_QUEUE_WIDTH,
    Math.max(MIN_PIECE_QUEUE_WIDTH, Math.round(unit * PIECE_QUEUE_COLUMN_UNITS)),
);

getLayout() 側の手順（操作重視のとき）：

  1. heightUnit = (canvasHeight - 2.4 - 2) / 24、widthUnit = getPlayPieceUnitBound(canvasWidth, gap)。
  2. unit = Math.min(heightUnit, widthUnit)、blockSize = unit - 1。
  3. queueWidth = getPlayPieceQueueWidth(unit)。
  4. 下限66pxが効いて fieldWidth + 2 × queueWidth + gaps > canvasWidth になった場合のみ、 確定した queueWidth を horizontalReserve として従来式で1回だけ再計算する （320×568などの極小幅の保険。反復は1回で収束する）。

(b) 操作重視：縦方向はパレット撤去分をNEXTへ回す

const available = fieldHeight - ceilingOffset;   // 天井合わせは維持
const cellHeight = clamp(22, targetCellHeight, 32);
const nextMinoHeight = clamp(
    MIN_PLAY_NEXT_MINO_HEIGHT,
    Math.floor((available
        - PIECE_LAYOUT_TOGGLE_HEIGHT          // 天井上に載る場合は 0
        - PLAY_RAIL_CHROME_HEIGHT
        - INFINITE_TOGGLE_HEIGHT              // 32
        - PLAY_RAIL_ROWS * cellHeight
        - NEXT_PANEL_CHROME_HEIGHT) / 5),     // 26
    Math.min(MAX_PLAY_NEXT_MINO_HEIGHT, Math.floor(queueWidth * 0.9)),
);

既存の getPieceRailMetrics() は「パレット12行／7行の2列フォールバック」を前提にしているため、 本設計で置き換える（PIECE_RAIL_ROWS_SINGLE / PIECE_RAIL_ROWS_DUAL / PIECE_RAIL_CHROME_HEIGHT* / MIN_SINGLE_COLUMN_* は操作重視では不要になる）。 railExtensionHeight（短い横持ち画面で右列をコメント予約領域へはみ出させる仕組み）は残すが、 必要行数が12→3に減るため実際にはほぼ発火しない。

(c) 選択重視：PAINT／SELECTの計算をそのまま使う

  • pieceQueueVisible = false となるため horizontalReserve = getEditorRailConfig(canvasHeight).reserve。 盤面サイズ・盤面位置・レール幅はPAINT／SELECTと完全一致する。
  • レール行数だけがPAINTと異なる（トグル行＋パレット11行）。 getResponsiveRailCellHeight() に行数を渡せるようにし、 SELECT_RAIL_ROWS_SINGLE = 20 / SELECT_RAIL_ROWS_DUAL = 13 を使う。

11-1. 目的

  1. PAINT・SELECT・PIECEの3つをひとまとまりの縦並びとして扱い、 上下に隣接したSELECT／PAINTの直上にPIECEを置く。

  3. PlayはAIと左右に隣接させ、左がPLAY・右がAIとする。
  4. Playの表示文言を Play から PLAY に改める。
設計の中心。第3版は「PIECEとPlayは対等な入口」という遷移の対等化だった。 第4版は視覚的なグルーピングを目的に合わせる。 PIECE・SELECT・PAINTは「盤面をどう編集するか」の排他的な編集モード3種なので縦一列にまとめ、 PLAYは「別画面へ行く」・AIは「探索を呼ぶ」という別種の操作なので、1行に併置して編集モード群から切り離す。 遷移仕様・選択状態の排他性・datatest属性・キュー寸法は第3版のまま変更しない。
