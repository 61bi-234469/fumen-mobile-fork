1. 目的

P1 は「自陣の手番を送って気になった地点を切り出す」を 1 画面で完結させ、 P2 は「相手盤面」と「フレーム共通軸」を足した。P3 は残る 1 つ、ガベージを足す。

依頼者の主目的は変わらず「特定状況の再現」である。P3 が主目的に効くのは次の 2 点。

  1. 切り出した局面の意味が変わる（FR-54） ―― ゲージに 4 行背負っている局面と、 ゲージ 0 の局面は、盤面が同じでもまったく別の局面である。 P2 までの切り出しは前者を後者として Editor へ渡していた。 ここを塞がないと「特定状況の再現」が成立しない場面が残る。
  2. 「なぜこの状況になったか」の最後の一片（FR-40〜45） ―― 自陣と相手盤面が 同一時刻で並んでも、その瞬間に何行保留されていて、次にどこへ穴が開いたかが見えなければ、 崩れた原因は読めない。とくに敗北ラウンドの検討は死因の可視化（FR-45）が中心になる。

本設計のスコープ判断

P2 の割り切り（盤面の更新粒度は lock 固定・落下描写なし）はそのまま維持する。 ガベージも同じで、ゲージ量とせり上がり予告は「その時点の値」を数値と図で出すだけとし、 せり上がりのアニメーションは作らない。すべて IR への参照だけで済み、エンジンの再実行は要らない （NFR-03 を維持）。
本設計は V-02（§3-7 / §8）を実施したうえで書いている。 「ゲージは記録済みイベント列だけから任意フレームで再構成できる（2,844 検査 / 不一致 0）」 「穴位置はエンジンの garbage.tank が正であり、.ttrm の ige.x は使えない（一致 30/355）」 の 2 点が実測で確定しているため、P3 の中核は推測に立っていない。

3-2. 中核: ガベージ parcel とゲージ恒等式

P3 の設計はこの一点に集約される。1 回の攻撃（iid）を 1 つの parcel として扱い、 その一生（受信 → 相殺／被弾）を記録する。 

// src/lib/ttrm/garbage.ts
export interface GarbageResolution {
    frame: number;
    kind: 'tank' | 'cancel';
    amount: number;
    column?: number;   // tank のみ。実際に穴が開いた列（0 始まり）
    size?: number;     // 穴幅
}

export interface GarbageParcel {
    iid: number;
    receivedFrame: number;
    amount: number;        // 受信時にキューへ入った行数（passthrough 相殺後）
    size: number;
    gameid?: number;       // confirm から。FR-44 / FR-45 用
    senderFrame?: number;  // 送信側クロックでの生成フレーム（V-01 で共通軸と実証済み）
    resolutions: GarbageResolution[];   // frame 昇順
}

ゲージ恒等式 ―― 任意フレーム f のゲージ量は次で求まる。

gauge(f) = Σ receive.amount − Σ cancel.amount − Σ tank.amount   （frame ≤ f のイベント）
V-02 でこの恒等式が エンジンの garbageQueue.size と全 2,844 検査点で一致した （不一致 0 件、実サンプル 2 本・34 プレイヤーラウンド）。 つまり ゲージは記録済みイベント列だけから完全に再構成でき、エンジンの再実行も lock ごとのスナップショットも要らない。

実装は「イベント直後のゲージ値」を累積した配列を 1 本作り、二分探索で引く。 ポイント空間（P2 §3-2）と同じ流儀で、IR にも state にも依存しない純関数に閉じる。 

gaugePoints: { frame: number, gauge: number }[]   // 昇順・イベント直後の値
gaugeAtFrame(timeline, f) → f 以下で最後の gaugePoint の gauge（無ければ 0）

「保留中」と「次にせり上がる行」は別物である

ゲージ（FR-40）とせり上がり予告（FR-42/43）は情報の性質が違う。 ゲージは「その瞬間にプレイヤーが見ていた保留量」で、当時の視界そのもの。 一方せり上がり予告は、リプレイである以上「実際に次に何がせり上がったか」という後知恵になる。 保留分は相殺されて結局せり上がらないこともあるため、両者は一致しない。 UI では予告側に「実測」であることが分かるラベルを付ける（§3-5）。 推測で穴位置を当てにいく必要はない ―― 答えは記録に残っている。

したがって「次にせり上がる行」は、保留中の parcel から予測するのではなく、 f より後の tank resolution を時刻順に取るだけで求まる。 

riseForecastAt(timeline, f, maxRows):
  frame > f の tank resolution を frame 昇順に取り、
  1 件 = { column, size, rows: amount } として maxRows 行ぶんまで返す

保留中 parcel の一覧（FR-41 の「受信 / 相殺 / 被弾を保持し表示する」）は parcel から引く。 

pendingParcelsAt(timeline, f):
  receivedFrame ≤ f かつ「amount − Σresolutions(frame ≤ f).amount > 0」の parcel を
  receivedFrame 昇順で返す
V-02 で parcel の収支が閉じることを確認済み ―― 605 iid のうち 596 が完全解決、 9 が終端時点で保留、収支破綻（受信していない iid の tank／過剰消費）は 0 件。 さらに「保留残の合計 == 終端ゲージ」が 34/34 で一致した。parcel モデルは実データで閉じている。

細部の規則

  • ゲージバーのスケール ―― 満尺は max(garbagecap, その時点までの最大ゲージ)。 garbagecap の既定は 8 で、実測の最大は 18（2,810 設置地点のうちゲージ 8 超は 19 地点）。 固定 8 だと稀に振り切れ、固定 18 だと普段が細すぎるため、この 2 段構えにする。 garbagecap 超過ぶんは色を変える（通常 赤 / 超過 橙）。
  • ゲージ 0 のときもバーの枠は残す。出たり消えたりすると盤面位置が横にずれ、 再生中ずっと目が泳ぐ。
  • 予告行は 1 行ぶんだけ描く（FR-42）。2 行以上保留されているときは 帯の右に +3 のように残数を添える（FR-43）。 複数行の穴位置を全部並べる案は、モバイル幅で読めないため採らない。
  • 相手側もゲージバーと予告行を出す。ただし narrow レイアウトでは バー幅 5px・予告行 6px と細くする。相手側に死因バッジは出さない （自陣の検討が主目的であり、両方出すと画面が死因だらけになる）。
  • ガベージマーカーは被弾（tank）を 赤、 相殺（cancel）を 緑 で描く。受信（receive）は描かない ―― 受信は必ず被弾か相殺のどちらかに解決されるので、3 色にすると密度が上がるだけで 読み取れる情報が増えない。
  • 非表示トグル（replayShowGarbage）を相手表示トグルの隣に置く。 既定は表示。オフにするとゲージバー・予告行・マーカー・死因バッジがすべて消え、 P2 と同じ見た目に戻る。切り出し時のゲージ保持（FR-54）はこのトグルに連動させない （§7-4）。

3-6. FR-54 ―― 切り出しにゲージを持ち込む

要件定義 FR-54 は「コメント or せり上がり行」と両論併記だったが、 コメント方式は本アプリでは成立しないことがコード上確定している。

Quiz.isQuizComment は comment.startsWith('#Q=') で判定する （src/lib/fumen/quiz.ts）。一方 comment_metadata.ts の既存方式は トークンを先頭に置き ' | ' で連結する（withSevenBagGrayProgress ほか）。 P1 以降、切り出しページのコメントは #Q= を先頭に持つため、 既存方式でトークンを足すと quiz として認識されなくなる。 末尾に足す案も、Quiz の NEXT 解析が ) 以降を全部ミノ列として読むため壊れる。 よってゲージはせり上がり行に載せる。

実装は次の 3 か所だけで済む。

// board_converter.ts
export const irFieldToField = (cells: IRField, sentLine?: IRField): Field

// ir_to_page.ts  ―― 第 5 引数として追加（既存呼び出しは省略可能）
export const irPointToPage = (
    cells: IRField, queue?: IRQueue, colorize = true, srs = true,

// actions/replay.ts の openReplayInEditor
const forecast = riseForecastAt(timeline, cursor.frame, 1);

  • せり上がり行は 穴の列（column から size 個）を空、残りを Piece.Gray で埋める。
  • flags.rise = true にする。fumen の意味論では「このページの lock 後にせり上がる」で、 Editor で操作対象ミノを置いた直後にガベージが上がる ―― リプレイの挙動と一致する。
